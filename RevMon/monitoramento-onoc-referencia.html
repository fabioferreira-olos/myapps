VMware / ESXi

Visao Geral dos Clusters

Os hosts ESXi rodam o hypervisor VMware — um SO proprietario onde nao se instala Zabbix Agent. O monitoramento e feito via vCenter API, que expoe metricas de hosts, VMs e clusters.

Inventario

Clusters: 2

Cluster OC02: Rack OC-02

Cluster OC08: Rack OC-08

Hosts ESXi: [definir qtde]

Como Monitorar

Metodo: vCenter SOAP API

Template: "VMware by HTTP"

Agente: Nenhum no ESXi

Requisito: Conta read-only no vCenter

⚠
Licao aprendida: Um coldstop ocorreu por falta de monitoramento de CPU/MEM nos hosts ESXi. Sem visibilidade, o cluster saturou ate nao conseguir manter as VMs. A implementacao deste monitoramento e prioridade maxima.
VMware / ESXi

Configuracao no Zabbix

O Zabbix conecta ao vCenter usando VMware collectors internos. Nao usa interface SNMP ou Agent — a coleta passa inteiramente pela API SOAP do vCenter.

Pre-requisitos no vCenter

Config Conta de servico no vCenter
  1. Criar usuario dedicado: zabbix-monitor@vsphere.local
  2. Atribuir role Read-only em Global Permissions
  3. Marcar "Propagate to children" = Sim
  4. Validar acesso: login no vSphere Client com a conta deve mostrar tudo em read-only

Configuracao do Zabbix Server

Config Parametros em zabbix_server.conf
  1. Editar /etc/zabbix/zabbix_server.conf
  2. Ajustar parametros:
# Collectors - minimo 2 (um por vCenter se houver mais de um) StartVMwareCollectors=2 # Intervalo de coleta (segundos) VMwareFrequency=60 # Coleta de performance counters VMwarePerfFrequency=60 # Cache - aumentar se muitos objetos VMwareCacheSize=32M # Timeout de conexao VMwareTimeout=30
ℹ
Apos alterar o conf, reiniciar o servico: systemctl restart zabbix-server

Criar Host no Zabbix Frontend

Config Registrar vCenter como host
  1. Configuration → Hosts → Create host
  2. Host name: vCenter-Olos
  3. Groups: VMware / Hypervisors
  4. Interfaces: Nenhuma (coleta via VMware collectors)
  5. Templates: Linkar "VMware by HTTP"
  6. Macros: Configurar conforme abaixo
# Macros no host do vCenter (Zabbix Frontend → Host → Macros) {$VMWARE.URL} = https://vcenter.dominio.local/sdk {$VMWARE.USERNAME} = zabbix-monitor@vsphere.local {$VMWARE.PASSWORD} = [senha_da_conta]
ℹ
Discovery automatico: Apos configurar, o template descobre automaticamente todos os Hosts ESXi e VMs. Eles aparecem como hosts individuais no Zabbix com items e triggers proprios.

VMware / ESXi

Runbooks

Procedimentos para os cenarios de incidente mais comuns nos clusters VMware.

Runbook Host ESXi com Alta CPU/Memory (Risco de Coldstop)
  1. Identificar: Qual host? Qual cluster (OC02 ou OC08)?
  2. Verificar cluster: Todos os hosts acima de 85%? Se sim → risco CRITICO de coldstop
  3. Top VMs: vCenter → Performance → identificar VMs com maior consumo
  4. DRS: Ativo? Ha recomendacoes de vMotion pendentes?
  5. Acao 1: Se DRS ativo → aprovar vMotions para balancear carga
  6. Acao 2: Se cluster saturado → identificar VMs nao-criticas para desligar
  7. Acao 3: Desligar VMs de dev/test/staging se existirem
  8. Escalar: Risco iminente → Lider de Infra imediatamente
  9. Prevenir: Abrir request para adicao de hosts ou migracao de workloads
Runbook Host ESXi Disconnected / Not Responding
  1. Ping: Host responde ICMP na management network?
  2. Se nao responde: Possivel crash ou perda de rede
  3. iDRAC: Acessar iDRAC via IP de management — servidor esta ligado?
  4. VMs: Se HA ativo → VMs devem reiniciar em outros hosts automaticamente
  5. Se HA nao atuou: Verificar configuracao de HA e isolation response
  6. Acesso fisico: Se necessario → chamado Ascenty para acesso ao rack
  7. Pos-recuperacao: Confirmar que host entrou no cluster e VMs estao saudaveis
  8. RCA: Logs do host (/var/log/vmkernel.log) + iDRAC lifecycle log
Runbook Reboot Inesperado de Host ESXi
  1. Detectado via: Trigger de uptime < 1h (bootTime resetou)
  2. Verificar VMs: Quais VMs estavam neste host? Foram reiniciadas pelo HA?
  3. iDRAC lifecycle: Evento de hardware (PSU, temperatura, DIMM)?
  4. vmkernel.log: Buscar por PSOD (Purple Screen of Death) ou panic
  5. Se PSOD: Coletar coredump e abrir SR com VMware/Broadcom
  6. Se hardware: Abrir chamado Dell ProSupport com Service Tag
  7. Documentar: Registrar timeline e causa raiz para historico
Switches / LAN

Visao Geral

Os switches fornecem a interconexao entre servidores e firewalls dentro de cada rack e entre racks. Um problema em switch afeta multiplos servidores simultaneamente.

Funcao

Interconexao intra-rack e inter-rack

Uplinks entre racks

Rede de management e producao

Monitoramento

Protocolo: SNMP (v2c ou v3)

Template: "Network interfaces by SNMP" ou vendor-specific

LLD: Discovery automatico de portas

Criticidade

Mudanca de speed ja causou incidente nao detectado

Latencia LAN elevada impactou comunicacao

Status anterior: Nao monitorado

⚠
Gap critico: Switches nao estavam no monitoramento. Mudanca de speed e latencia LAN foram detectados somente no momento do impacto ao servico. Todo o monitoramento desta secao e novo.
Switches / LAN

Configuracao no Zabbix

Adicionar cada switch gerenciavel ao Zabbix via SNMP para coletar metricas de portas, trafego e erros.

Config Adicionar Switch ao Zabbix
  1. Inventariar: Listar switches gerenciaveis (marca, modelo, IP management, rack)
  2. Habilitar SNMP: No switch, configurar community (v2c) ou usuario SNMPv3
  3. Zabbix Frontend: Configuration → Hosts → Create host
    • Host name: SW-OC01-01 (exemplo)
    • Groups: Switches / Network
    • Interface: SNMP, IP do switch, porta 161
  4. Template: Linkar conforme vendor:
    • Generico: "Interfaces by SNMP"
    • Cisco: "Cisco IOS by SNMP"
    • Dell: "Dell Force10 by SNMP"
    • HP/Aruba: "HP Enterprise Switch by SNMP"
  5. Macro: {$SNMP_COMMUNITY} = community string configurada
  6. Validar: Executar LLD discovery e confirmar que portas ativas aparecem
ℹ
O template generico "Interfaces by SNMP" funciona em qualquer switch que suporte ifTable/ifXTable (praticamente todos os gerenciaveis). Use templates vendor-specific apenas se precisar de metricas extras como CPU/MEM do switch.

Switches / LAN

Monitoramento de Latencia LAN

Em uma LAN saudavel, latencia entre equipamentos deve ser inferior a 1ms. Valores acima de 2ms indicam problema. Usar probes ICMP entre pontos estrategicos.

Config Implementar Probes de Latencia Intra-site
  1. Definir pontos de medicao: IPs representativos em cada rack
    • Firewall management IP de cada rack
    • Switch management IP (ou 1 servidor por rack)
    • vCenter / ESXi management IPs
  2. Criar items no Zabbix (no host do Zabbix Server/Proxy ou em um servidor com agent):
    • icmppingsec[ip_destino,,,,] → RTT em segundos
    • icmppingloss[ip_destino,,,,] → packet loss %
    • Intervalo: 30 segundos
  3. Pares criticos minimos:
    • Firewall OC-02 ↔ ESXi hosts OC-02
    • Firewall OC-08 ↔ ESXi hosts OC-08
    • Inter-rack: OC-02 ↔ OC-08
    • Rack telecom ↔ Rack dados (ex: OC-01 ↔ OC-02)
  4. Triggers: RTT > 2ms warning, > 5ms high, > 10ms critical
ℹ
Baseline: Nos primeiros 7 dias, apenas coletar dados sem triggers para estabelecer o valor normal. Ajustar thresholds baseado na realidade do ambiente.

Switches / LAN

Runbooks

Procedimentos para cenarios de incidente na rede LAN.

Runbook Porta DOWN com Servidor Conectado
  1. Identificar: Qual switch? Qual porta? Qual servidor esta conectado?
  2. Redundancia: Servidor responde por outra interface? (NIC teaming/bonding)
  3. Fisico: Cabo conectado? LED da porta aceso?
  4. Admin status: Porta foi desabilitada? (ifAdminStatus = 2 = shutdown)
  5. Se admin UP + oper DOWN: Problema fisico (cabo, SFP, porta defeituosa)
  6. Teste 1: Mover cabo para outra porta do switch
  7. Teste 2: Testar com cabo reserva
  8. Se porta defeituosa: Migrar permanentemente, documentar porta danificada
  9. Acesso fisico: Se necessario → chamado Ascenty
Runbook Latencia LAN Elevada (>5ms)
  1. Escopo: Latencia em um caminho especifico ou generalizada?
  2. Se generalizada: Possivel saturacao de uplink ou broadcast storm
  3. Port utilization: Alguma porta de uplink/trunk acima de 85%?
  4. Erros: Portas com alto rate de errors/discards no caminho?
  5. Spanning-tree: Mudanca de topologia STP recente? (logs do switch)
  6. ARP/MAC table: Entries excessivas indicam loop ou ataque
  7. Se porta com erros: Verificar cabo/SFP naquele segmento
  8. Se saturacao: Redistribuir carga ou avaliar upgrade de uplinks
  9. Documentar: Registrar baseline normal para comparacao
Runbook Erros Excessivos em Porta (>50/min)
  1. Tipo: CRC? Frame errors? Alignment?
  2. CRC errors: Geralmente = cabo danificado, SFP com problema, interferencia
  3. Discards: Buffer overflow (porta congestionada) ou policy drop
  4. Duplex: Mismatch entre switch e dispositivo?
  5. Speed: Mismatch pode gerar late collisions
  6. Acao - cabo: Substituir patch cord, testar com cable tester
  7. Acao - SFP: Verificar potencia optica (DOM), limpar conectores
  8. Se persiste: Trocar porta no switch, documentar defeito
Runbook Port Speed Abaixo do Esperado
  1. Identificar: Qual porta? Speed atual vs esperado? (ex: 100M ao inves de 1G)
  2. Verificar outro lado: O servidor tambem mostra speed reduzido?
  3. Auto-negotiate: Ativo em ambos os lados? (recomendado para copper)
  4. Cabo: Cat5e/Cat6 para 1G? Cabo pode estar degradado
  5. Teste: Reconectar cabo em ambos os lados
  6. Teste: Substituir cabo por um reserva sabidamente bom
  7. Se problema persiste: Fixar speed manualmente em ambos os lados (switch + NIC)
  8. Documentar: Registrar qual porta/servidor tinha o problema e resolucao

Gap Analysis

Problemas recentes mapeados contra lacunas de monitoramento, com plano de acao.

ProblemaLacunaAcaoPrioridade
Coldstop do cluster VMware Sem monitoramento de CPU/MEM dos hosts ESXi Integrar Zabbix com vCenter API. Triggers em 70/85/95%. P1
Restart de hosts ESXi nao detectado Sem monitoramento de uptime/bootTime Monitorar runtime.bootTime. Trigger: uptime < 1h. P2
Mudanca de speed das portas Switches nao monitorados, sem coleta de ifSpeed SNMP nos switches + trigger ifHighSpeed < baseline. P2
Latencia na rede LAN Sem ICMP intra-site, sem monitoramento de port errors Probes ICMP entre pontos criticos + ifInErrors/ifOutErrors. P2

Checklists Periodicos

Verificacoes de rotina para o time ONOC referentes a VMware e Switches.

Diario — Inicio de turno

Checklist Verificacao Diaria
  1. Zabbix: alertas ativos de VMware ou Switches nao tratados?
  2. Todos os hosts ESXi com connectionState = connected?
  3. Algum host ESXi com CPU ou MEM acima de 70%? (tendencia)
  4. Probes de latencia LAN: algum acima de 2ms nas ultimas 24h?
  5. Portas de switch com erros crescentes?
  6. Algum alerta de port speed mismatch?

Semanal

Checklist Verificacao Semanal
  1. Clusters VMware: capacity planning — CPU/MEM total vs utilizado (projecao)
  2. Snapshots de VMs: algum com mais de 3 dias?
  3. Port errors acumulados nos switches: tendencia crescente em alguma porta?
  4. Reboots de hosts ESXi na semana: algum nao planejado?
  5. Verificar se todos os switches e hosts novos estao no monitoramento

Mensal

Checklist Revisao Mensal
  1. Revisar incidentes do mes: novo gap identificado?
  2. Thresholds geraram falso-positivos? Ajustar se necessario
  3. Capacity planning formal: projecao 3-6 meses para compute
  4. Validar que LLD descobriu todos os objetos (novos hosts, VMs, portas)
  5. Atualizar este documento com novos aprendizados
